# M1.5A — Supervised additive mission planning

An owner can extend an existing **approved AI mission** without regenerating its original
plan. Accepted Researcher outputs and original task/run/review records remain unchanged.
Mock missions, drafts, cancelled missions and missions still awaiting original-plan review
are ineligible. This is planning only: no external tools, browsing, autonomous workers,
Developer execution or new provider integration.

## Architecture and authorization

`mission_extensions` is an independent, versioned generation-run/proposal ledger. Its ID
is the extension run/provenance ID; request UUID, requesting `auth.uid()`, workspace/mission,
instruction, immutable context/fingerprint, model/provider, lease, timestamps, generated
candidates and terminal status are retained. It does not insert into `public.runs`, so the
original three-attempt planning history and Researcher's three-attempt task budget cannot
be consumed/reset by extensions. Each extension request permits **one provider request**;
failed/interrupted requests need a new request UUID, explicit cost consent and fresh owner
authorization. Reusing a request UUID never resumes generation.

The server authenticates and calls the owner-only `begin_mission_extension` RPC. PostgreSQL
locks the mission, checks scope/state/consent, rejects active original/Researcher runs or
another open extension, builds the bounded snapshot and records a 120-second capability-
bound lease. Capabilities, context and fingerprints are not SELECT-granted to clients.
`finish_mission_extension` is service-role-only with no caller-supplied actor IDs. It
rechecks the lease and original requesting owner's current membership, validates output,
and atomically retains a reviewable proposal, a stale proposal or failure. Provider or
persistence failures never trigger a second call or overwrite an ambiguous success.

Context includes mission title/objective; every existing task's ID, shortened title, role,
plan decision/status and execution/review status; the latest five accepted deliverable
summaries; latest five prior extension statuses/summaries; and the new instruction. Bounds:
30 existing tasks (including rejected originals), title excerpts 160 chars, objective
2000 chars, accepted summaries 500 chars, prior summaries 200 chars, instruction 2000
chars and serialized snapshot **12,000 UTF-8 bytes**. Oversized snapshots fail before
a generation-run row/provider request is created; content is not silently omitted beyond the documented excerpt
limits. Input is byte-bounded, not counted by a live tokenizer/API. Output is capped at
**4000 tokens**, one candidate, at most eight tasks, strict text/role/priority/dependency
validation. Maximum-sized text may exceed the output-token budget; truncation is a failed
proposal, never partial tasks or an automatic retry.

A fixed system instruction treats all mission/artifact/user content as untrusted. The
existing Gemini structured transport is reused, with no OpenAI fallback or inherited
Researcher 503 retry. Model settings are unchanged (`GEMINI_MODEL` stays server-side).
Generation has at most 30 seconds, also bounded by 45 seconds from action entry. RPCs have
5-second claim/10-second finalization deadlines, no SDK retries and a 55-second outer
signal against the dashboard's existing 60-second runtime. Authentication/platform or
network interruption can still leave a leased run. Refresh first; an owner can recover
only an expired running extension, without another provider call.

## Review, history and concurrency

Only one running/unreviewed extension is allowed per mission. Concurrent requests serialize
on the mission row and a partial unique index. Multiple successive approved/rejected/
failed extensions are supported; the bounded context limits still apply as projects grow.
Original Researcher authorization remains independent: if the owner starts/changes existing
work while an extension is pending, that extension may become stale.

The fingerprint covers full relevant mission fields, complete task state, original/Researcher
runs, artifacts, original/execution reviews and prior finalized extension history, not just excerpts. Generation finalization marks changed context stale.
Review locks mission/proposal and rechecks the fingerprint and active runs. A stale approval
attempt commits a stale marker and applies **zero** tasks; only rejection or a fresh
proposal is available. Snapshot-scoped dependency validation preserves stale output for
audit even if its formerly eligible task changed after generation.

`mission_extension_reviews` records an immutable complete selection. Checked positions
become approved assigned rows in **public.tasks**, linked to extension ID/position. All
unchecked candidates remain permanently rejected in the immutable proposal/review history.
Confirming an empty selection records rejection, never an empty approval. Roles resolve
to existing workspace agents on the server, without enabling them. Suggested dependencies
may reference eligible snapshot tasks or earlier additions only; accepting a dependent
addition requires accepting its earlier addition dependencies. Dependencies are metadata,
not executable scheduling instructions.

Request/review UUID uniqueness, immutable review records and a unique extension/position
index prevent duplicate tasks. An exact same-actor review replay returns the prior review;
conflicting decisions or reused IDs fail. Task creation, review, proposal status and audit
events share one transaction, including rollback on a late audit failure. Triggers freeze
request/context/output history, terminal decisions and approved extension task rows.
RLS scopes reads to workspace members; client tables remain SELECT-only, with restricted
extension columns. No broad grants or existing M1.3/M1.4 RPC authorization changes.

**Execution boundary:** approved additions are actual assigned mission tasks, but execution
is deliberately unavailable in M1.5A. They have no original-plan review/run IDs and remain
`execution_status=not_authorized`. Database constraints/triggers and M1.4's provenance checks
prevent reusing the original review to execute them, even with forged UI requests. Future
execution support must explicitly validate extension-review provenance in a separate
reviewed milestone, not relax the guards. Original approved Researcher tasks continue
through the unchanged M1.4 authorization/execution/review path.

The dashboard separates original tasks, extension candidates/history and approved additions.
It shows explicit cost consent, pending/error/recovery states, per-task selection and full
review confirmation, assignment and original-vs-added provenance. Disabling new generation
retains existing extension review/history UI once the schema is present. Page load and
refresh never call Gemini. Sanitized `agent_city.extension` diagnostics include stage,
run ID, elapsed time and safe SQL/provider codes; never instructions, artifacts, hashes,
keys or raw provider responses.

## Activation and rollback (manual, not performed)

1. Review current deployed schema/history and confirm M0–M1.4.1 compatibility, including
   task constraints, Researcher columns and original RPCs. Historical remote migration
   IDs differ from local M0/M1.1 filenames and M1.2 was manually applied: do not reconcile
   those IDs or run `supabase db push`.
2. Apply **only** `supabase/migrations/20261023120000_dynamic_mission_planning.sql` through
   an atomic tracked migration after approval. It adds two history tables and nullable
   `tasks.extension_id`, narrowly extends the non-execution constraint, and adds scoped
   RPCs, RLS, indexes and history guards. It does not update historical rows or migrations.
   Stop on schema drift; verify original tasks (new column null), accepted artifacts,
   task review decisions, attempt counts, SELECT-only grants and function ACLs.
3. Deploy separately after review. Default `AGENT_CITY_MISSION_EXTENSIONS_ENABLED=false`
   is safe before migration (only absent-table errors are tolerated while disabled).
   Generation requires `AGENT_CITY_MODE=supabase`, the existing server-only Gemini/service
   keys and existing configured `GEMINI_MODEL`. No NEXT_PUBLIC keys or model changes.
   Confirm the effective hosted runtime supports the existing 60-second page budget.
4. Explicitly enable `AGENT_CITY_MISSION_EXTENSIONS_ENABLED=true`. No planning or Researcher
   flags need to be enabled just to extend an already-approved mission. All original
   flags and authorization policies remain independent.
5. Use one small owner-authorized instruction on an existing approved mission with an
   accepted Researcher artifact. Verify one new extension request/provenance ID, model
   metadata, candidates only, no original-run increment and no task/artifact mutations.
   Confirm a partial selection, verify assigned new tasks, retained rejected candidates,
   audit/history, and unchanged original Researcher acceptance. Confirm no new execution.
6. Verify duplicate submission cannot create extra tasks; review a changed-context proposal
   and confirm stale rejection. On ambiguous persistence, refresh before trying recovery;
   recover only expired running extensions. A new generation requires fresh paid-call consent.
7. Roll back by disabling the new-generation flag; existing history/review remains available
   in this application version. If needed restore the previous application separately.
   Retain the additive schema, approved additions, rejected proposals, guards and histories.
   Do not delete records, replay migrations, reset counts or drop constraints to regain
   execution. Old original-plan queries exclude additions, so previous workflows retain
   their original provenance. No destructive down migration is provided.

## Offline verification and limitations

`npm run check` includes Node/PGlite, Python, existing M0–M1.4.1 HTTP regressions, new
`npm run test:extensions-http`, typechecks and production build. Tests cover populated
accepted-artifact compatibility, owner/member/anon/isolation/revocation, consent, output
and dependency validation, timeouts, context bounds, partial/whole rejection, repeated
extensions, immutable history, duplicate/concurrent submissions, stale generation/review,
lease recovery, assignment/audit rollback, and no automatic execution. HTTP fixtures run
real Next.js/server actions against synthetic loopback Supabase/Gemini endpoints and block
external provider traffic. PGlite concurrency is serialized on one connection; hosted
independent PostgreSQL sessions, actual Vercel budgets and live model quality/latency are
not verified. No remote migration, live model call, merge or deployment is part of delivery.
