## M1.2 provider extension

`AGENT_CITY_AI_PROVIDER=gemini|openai` selects exactly one provider, defaulting to
`gemini` only when planning is explicitly enabled. Gemini uses `GEMINI_API_KEY`
and optional `GEMINI_MODEL` (default `gemini-flash-latest`); OpenAI keeps
`OPENAI_API_KEY` and optional `OPENAI_MODEL` (default `gpt-4.1-mini`). The existing
server-only binding supplies credentials to the provider abstraction. Gemini uses one
REST `generateContent` request; OpenAI retains its official SDK. Both use the same plan
schema, 45-second deadline and 6,000-output-token cap. There are no transport retries,
automatic provider switches or fallbacks. Quota/rate-limit errors fail the current
attempt with the existing sanitized `provider_error` code. No tools are configured.

Default model support was checked on 2026-10-21 against Google's official sources:
[SDK examples](https://github.com/googleapis/js-genai/blob/main/README.md) use
`gemini-flash-latest`; the [model catalog example](https://github.com/google-gemini/cookbook/blob/main/quickstarts/Models.ipynb)
lists it, and the [structured JSON example](https://github.com/google-gemini/cookbook/blob/archive/generate-content-api/quickstarts/JSON_mode.ipynb)
demonstrates Flash structured output. Google's [unpaid API-key guidance](https://github.com/google-gemini/gemini-cli/blob/main/docs/resources/quota-and-pricing.md#log-in-with-gemini-api-key-unpaid)
permits Flash models. This is documentation verification, not a live model call or a
check of your account quota. The alias can change; pin a supported Flash model with
`GEMINI_MODEL` if desired. Free access depends on account/region/quota; do not enable
billing automatically or assume that a key on a paid project is free.

M1.2 requires **only** the new additive migration
`supabase/migrations/20261021140000_multi_provider_planning.sql`. It extends
`runs.adapter` to record Gemini accurately, adds a provider-aware claim overload,
and shares the three-attempt budget across both providers. The old three-argument
OpenAI RPC and in-flight OpenAI finalization remain supported. Lease fencing, owner
checks, SELECT-only client grants, RLS and human-review-only proposals are preserved.
Deploy it only after separately approved remote schema checks, using an atomic tracked
migration operation and reloading the PostgREST schema cache. Do not replay M0/M1.1:
M1.1 was reported applied remotely as version `20261021130453`, name
`chief_of_staff_plan`; its local filename intentionally remains unchanged.

`npm run test:planning-http` now exercises both providers with intercepted loopback
responses. Provider tests cover selection, missing keys, invalid configuration,
schema rejection, quota/rate limits, disabled mode and no paid fallback. No live
inference, deployment, migration application or AI enabling is part of this change.

## Architecture and authorization

- The dashboard offers **Authorize Chief of Staff plan** to workspace owners on a
  draft mission (or a failed AI planning mission with attempts remaining).
- An unchecked/missing authorization is rejected server-side. Authorization explicitly
  covers one potentially paid call and disclosure of the mission title/objective to OpenAI.
  Existing approval for `mock_run` does not authorize planning.
- The server action verifies the Supabase session using `auth.getUser`. The authenticated
  `begin_chief_plan` RPC locks the mission, verifies owner membership using `auth.uid()`,
  records an approved `chief_of_staff_plan` scope, claims a run and switches the mission
  to `execution_mode=chief_of_staff`. Only this successful claim permits a model call.
- For OpenAI, the official JavaScript SDK calls Chat Completions with strict JSON Schema,
  no tools, a 6,000-token output limit, a 45-second deadline and **zero SDK retries**.
  The endpoint is fixed to `https://api.openai.com/v1`; SDK logging is off. Mission input
  is treated as untrusted data. No user/session IDs or credentials go into the prompt.
- Zod validates the response before persistence. A successful response must have
  `finish_reason=stop`, no refusal, and exactly the expected keys. PostgreSQL independently
  validates the same shape and bounds before committing the artifact and proposed tasks.
- A separate, cookie-free service-role client calls **only** `finish_chief_plan`.
  Finalization takes a run ID and per-invocation random capability hash, **no actor ID**.
  The actor is read from the run's authenticated claim. Both run/mission state and lease,
  original approval, and current ownership are rechecked. Authenticated/anonymous clients
  cannot execute either the public or private finalizer (including with direct default
  EXECUTE grants). Its helpers use fixed empty search paths.
- All original table RLS and SELECT-only client grants remain intact. New data uses
  existing workspace-scoped tables. The privileged key inherently bypasses RLS: keep it
  server-only and scoped in application code to finalization; never use it for user reads.
- Success commits one JSON artifact and ordered `tasks` with `status=proposed`, no assigned
  agent, suggested role and expected deliverable. Mission status becomes `awaiting_approval`.
  The dashboard displays the plan, risks and non-executable proposals for human review.
  There is **no task execution, delegation, plan-approval RPC or autonomous follow-up**.
  Further execution requires a separately implemented and reviewed human approval gate.
- Existing mock transitions reject every AI mission. The renamed M0 helper is no longer
  executable by clients. Mock missions continue through the unchanged M0 lifecycle.
  The existing disabled agent-instance flags do not enable execution; the M1.1 feature
  flag exclusively controls this supervised planning entry point.

## Structured output

Exactly `{ summary, tasks, risks }`:

| Field | Bounds |
| --- | --- |
| summary | 1–2,000 nonblank characters |
| tasks | 1–12; array order is proposal order |
| task.title | 1–200 nonblank characters |
| task.suggested_agent_role | `chief-of-staff`, `researcher`, or `developer` |
| task.expected_deliverable | 1–2,000 nonblank characters |
| risks | 0–10 strings, each 1–500 nonblank characters |

Unknown fields, invalid types and empty content are rejected. React renders model output
as text, never HTML. Suggested roles are labels, not delegation instructions.

## Failure, duplicates and recovery

Mission row locks plus the existing unique running-run index serialize claims. Each
mission permits at most **three authorized attempts**, including interrupted claims.
No automatic model retry or silent mock fallback occurs. A finished plan cannot be
regenerated or completed through mock actions.

Timeout, provider failure/refusal and invalid output store a sanitized failure code,
mark the run/mission failed, and persist no plan/tasks. A retry requires fresh owner
consent. Provider error bodies, prompt data, credentials and capability hashes are never
returned to the browser. Attempts are not a billing guarantee: a timeout may still cost
money; the platform cannot cancel or roll back provider-side processing.

A process interruption or uncertain finalization leaves a two-minute lease. Refresh first:
finalization may have committed despite a lost response. If still running after expiry,
an owner can choose **Recover interrupted plan**, which marks it failed without a model
call. Only then may they explicitly authorize another attempt (within the same limit).
Expired/stale finalizers are rejected even after recovery/retry. Recovery and existing
plan display remain available if the feature flag is subsequently disabled. Disabling
new planning does not cancel a call already in flight.

## Server environment

| Variable | Requirement |
| --- | --- |
| `AGENT_CITY_MODE` | `supabase`; mock mode always rejects AI planning |
| `AGENT_CITY_AI_PLANNING_ENABLED` | Defaults off; only exact `true` enables calls |
| `AGENT_CITY_AI_PROVIDER` | `gemini` (default) or `openai`; never switches automatically |
| `GEMINI_MODEL` | Optional; defaults to `gemini-flash-latest` |
| `GEMINI_API_KEY` | Server-only Gemini credential when Gemini is selected |
| `OPENAI_MODEL` | Optional; defaults to `gpt-4.1-mini`; must support strict structured output |
| `OPENAI_API_KEY` | Server-only OpenAI credential; never `NEXT_PUBLIC_` |
| `SUPABASE_SERVICE_ROLE_KEY` | Server-only service-role JWT or secret key; finalization only |
| `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` | Existing user-scoped M0 configuration; do not replace the public key with a privileged one |
| `SUPABASE_PROJECT_REF` | Existing optional project consistency guard |

The M0-only advice against configuring privileged keys still applies to ordinary clients:
M1.1 adds this one isolated server finalizer. Never send either secret to the browser,
commit it, or log it. Use secure server environment settings. Production requests require
HTTPS access to the configured Supabase project and the selected provider: `generativelanguage.googleapis.com` or `api.openai.com`. Dashboard runtime
is Node.js with `maxDuration=60`; confirm the hosting plan supports that duration.
M0 remains usable with planning disabled and without either additional credential.

## Local acceptance

Node 24, Python 3.12 and uv are required. From the existing isolated checkout (no worktree
needed): `bash scripts/setup.sh`, then `npm run check`.

- `npm test`: domain/config tests, embedded PostgreSQL migrations, RLS, RPC ACLs,
  ownership, capability mismatch, invalid-plan rollback, ordered persistence, stale
  finalizers, owner revocation, mock isolation, maximum attempts and recovery; official
  SDK requests intercepted by an in-memory fetch fixture; no live network/provider.
- `npm run test:runtime`: four Python boundary/adapter tests; real adapter remains disabled.
- `npm run test:auth-persistence`: existing Next.js + loopback Supabase HTTP fixture,
  with planning explicitly disabled, preserving M0 login, refresh and lifecycle behavior.
- `npm run test:planning-http`: same application over HTTP with synthetic credentials;
  a **test-process-only preload** blocks external fetches and routes SDK requests to the
  loopback fixture. Exercises consent/session denials, exact claim/finalizer payloads,
  stored plan/proposal UI, no credential disclosure, and duplicate rejection before another
  provider request. PostgreSQL behavior is validated separately by the SQL tests.
- `npm run typecheck` and `npm run build`: required. No keys or enabled flag needed to build.

The fixtures do not validate hosted Supabase/PostgREST configuration, actual provider
schema acceptance/quality, Vercel runtime limits or browser interaction. Those remain
explicitly approval-gated remote acceptance checks. Local success does not establish
remote activation or restore the lost implementation's previous test count/checksum.
