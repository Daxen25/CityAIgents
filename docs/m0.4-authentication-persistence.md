The Agents page previously displayed the shared hard-coded templates even in Supabase

## Existing workflow and RPC mapping

The Next.js server actions validate form input and require a server-verified user before
workspace/mission mutations. Per-request Supabase SSR clients use the user's session and
a publishable key, never an admin/service-role key. The Data API defaults to the public
schema, so these calls target the three existing public functions:

| UI action | Repository call | Public function and arguments |
| --- | --- | --- |
| Create first workspace | `createWorkspace(name)` | `create_workspace(workspace_name)` |
| Create mission draft | `createMission(user,input)` | `create_mission(wid,mission_title,mission_objective,mission_kind)` |
| Submit/approve/reject/start/complete/fail/cancel | `transition(user,id,action)` | `transition_mission(mid,requested_action)` |

The dashboard SELECTs `workspaces`, `workspace_members`, `missions`, `approvals` and
`activity_events` through the user's RLS-protected client. The Agents page SELECTs
`agent_definitions`. There is no fallback to local state on a Supabase error.
Successful actions revalidate the dashboard and redirect back to persisted reads.

Supabase Auth uses `signInWithPassword`, validated with `auth.getUser()` on the server.
The Next.js proxy refreshes expired sessions and passes updated cookies both to the
current server request and the browser; responses prohibit storage. Logout uses
`signOut({scope:'local'})` and handles errors. Mock cookies do not authenticate a user
in Supabase mode. No browser Supabase client or privileged frontend credentials are used.

## Exact manual browser acceptance procedure

### Configure and start

Use an **existing confirmed email/password account** in this Supabase project. If none
exists, the project owner must create/confirm it separately; the application does not
provide signup and this milestone does not create users. Keep credentials out of chat,
source control, screenshots and logs.

Ensure these settings are injected securely or present in ignored `apps/web/.env.local`:

```dotenv
AGENT_CITY_MODE=supabase
SUPABASE_URL=https://atbksxlqgfxvetsgusek.supabase.co
SUPABASE_PROJECT_REF=atbksxlqgfxvetsgusek
SUPABASE_PUBLISHABLE_KEY=<project publishable key or legacy anon key>
```

Inherited environment values take precedence over `.env.local`. Do not set a service-role
key or `AGENT_CITY_ALLOW_LOCAL_MOCK` for this workflow. No OpenAI key is needed.

```bash
cd /workspace/CityAIgents  # or your local checkout
npm run dev
```

For this cloud proxy environment, use `NODE_USE_ENV_PROXY=1 npm run dev` so outbound server
requests honor the configured HTTPS proxy. A personal local checkout typically does not
need that flag. The app listens on loopback port 3000 by default. Open its `/login` route
in your local browser; this onboarding UI does not supply a public web preview.

### Login and protected routes

1. In a private browser window, visit `/dashboard`, `/dashboard/agents` and
   `/dashboard/activity`. Each must redirect to `/login` before sign-in.
2. Confirm the login page has Email and Password fields and **Sign in**, with no mock
   workspace entry button. A failed login must show the generic error and remain signed out.
3. Sign in with the existing confirmed account. Expect `/dashboard` and the
   **SUPABASE · authenticated workspace · mock execution only** banner.
4. Open Agents. Expect the three persisted Chief of Staff, Researcher and Developer
   definitions and their stored versions. A database error must not silently show templates.

### Workspace, mission and persistence

These explicit browser actions write the intended user's application records; they do
not change the schema, migration history, Auth users or Storage configuration.

5. If the account has no workspace, submit **Create your first workspace** with a clear
   test name such as `M0.4 acceptance`. This calls `public.create_workspace`; expect the
   workspace selector and new-mission form after redirect. Workspace ownership is assigned
   by SQL to the authenticated user. Existing workspaces should already be listed.
6. Create a personal mission titled `M0.4 persistence check` with objective
   `Verify authenticated mission persistence without external actions.` Expect a draft.
   This calls `public.create_mission`.
7. Refresh the page and open `/dashboard` in another tab of the same browser. Expect the
   same workspace and mission, without duplicates. This checks persisted reads.
8. Click **Request approval**, then **Approve mock run**, **Start mock run** and
   **Complete mock run**. Each action calls `public.transition_mission`. Observe draft ->
   awaiting approval -> approved -> running -> completed. Start must not be offered before
   approval. This simulates lifecycle status only; no AI work or external tool executes.
9. Visit Activity, confirm the recorded actions, reload and return to the dashboard.
   The completed mission and activity must persist. No unrelated workspace should appear.

### Refresh, logout and fresh login

10. Leave the signed-in browser until its access token expires (project-configured TTL,
    commonly about one hour), then navigate/reload `/dashboard`. Expect to stay signed in
    through the existing refresh token. In browser Network tools, check the navigation's
    `Set-Cookie` behavior and `Cache-Control: no-store` without sharing cookie/token values.
    Do not alter production Auth TTL or paste/edit JWTs just to speed up this test.
11. Click **Sign out**. Expect `/login`. A fresh request to each protected route must
    redirect back to login. If browser Back shows a cached page, reload it to verify that
    protected data is no longer available; mutations must also require a current user.
12. Sign in again with the same account. Expect the same saved workspace, completed
    mission and recorded activity. This confirms persistence across sessions.

Optional: with another **already existing** account, verify that it cannot see the first
account's private workspace/mission. Do not create Auth users or insert membership fixtures
automatically for this check.

## CLI verification versus browser sign-in

`SUPABASE_VERIFY_ACCESS_TOKEN` is optional for normal browser usage. The browser obtains
its own session when the user signs in; there is no requirement to manually copy tokens
for the application to work.

For the separate read-only `npm run verify` command to fully pass, securely configure a
valid unexpired access token for an existing user, then run:

```bash
npm run verify
```

Without it, exit 2 is expected and authenticated SELECT remains unverified. The script
does not sign in, refresh tokens, call mutation RPCs or inspect migration history. Never
share token values in chat or commit them. Token expiry requires a fresh existing-user
token; the CLI does not refresh it automatically.
