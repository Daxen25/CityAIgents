# M1.3 — Human plan review and task assignment

Owners can review an existing completed Chief of Staff plan, select individual proposals
and explicitly confirm approval or reject the entire plan. Unselected tasks are rejected,
retained and auditable. An approved plan must accept at least one task. Acceptance creates
no new run, provider request or execution permission. Planning and mock flows are unchanged.

## Persistence and security

`review_task_plan(mid, rid, accepted_ids, decision, confirmed, request_id)` uses the current
Supabase session, never a service-role key or a caller-provided actor. The private definer
checks workspace ownership, AI mission status, completed planning run, matching artifact
and exact persisted task set. It resolves assignments against the workspace's existing
agents and versioned definitions using each task's suggested role. Disabled agent flags
remain disabled. There is no task reassignment endpoint.

One immutable application review is stored in `task_plan_reviews` per mission/run, with
owner ID, timestamp, accepted IDs and a canonical snapshot of every decision/assignment.
Each task keeps its original mission/run/position and gains a review reference. Paid-model
`approvals` are left intact: permission to create a plan is not reused as task approval.
Task and plan decisions create activity events in the same transaction.

The mission row lock serializes competing reviews and the existing planning RPCs. Exact
replays of the same request ID, actor, mission/run and decisions return the stored review
without new events. A conflicting submission fails; a request ID cannot be reused on
another mission. Partial task updates, failed audit writes and constraint failures roll
back the entire review. All existing RLS and SELECT-only client table grants remain;
the new table is member-readable and client writes are RPC-only. Both public and private
review functions explicitly deny anonymous execution, including direct default grants.

Approved tasks have `status=approved` and a scoped agent assignment; rejected tasks have
`status=rejected` and no assignment. A database check disallows running/completed status
for any plan-linked task in M1.3. Mock mission RPCs still reject AI missions, including
approved ones. AI missions become `approved` or `cancelled`; no task is marked executed.

The dashboard shows AI/mock labels, individual status/deliverable/role, assignment,
reviewer/time, retained rejections and counts. Review works with AI planning disabled and
without provider or service-role credentials. The exported core `SupervisedTaskHandoff`
type describes a future M1.4 boundary and has `executionAuthorized: false`. A future
adapter must revalidate stored provenance and obtain fresh execution approval; a client
descriptor cannot authorize execution. No adapter,
worker, tools, external repository access, n8n or execution RPC is implemented.

## Additive migration and compatibility (remote operation not performed)

Apply **only** `supabase/migrations/20261022090000_task_plan_review.sql` after separately
approved activation. It adds the review table/RLS, nullable task review FK, two statuses,
the guarded proposal constraint and one owner-only RPC. No historical file is changed,
no existing mission/run is rewritten and no model configuration is enabled.

Before activation, verify the correct Supabase project and inspect remote migration history
and catalog definitions read-only. M0/M1.1 remote version IDs differ from local filenames
(M1.1 was reported as `20261021130453`); M1.2 was applied manually. Missing/mismatched history
is not permission to replay SQL or automatically reconcile IDs. Do not use blanket
`supabase db push`, reset, replay or repair operations.

Compatibility checks (SQL Editor, read-only):

```sql
select version, name from supabase_migrations.schema_migrations order by version;
select to_regclass('public.task_plan_reviews') as already_installed,
       to_regprocedure('private.workspace_role(uuid)') as membership_helper,
       to_regprocedure('private.validate_chief_plan(jsonb)') as plan_validator,
       to_regprocedure('public.begin_chief_plan(uuid,text,text,text)') as provider_claim,
       to_regprocedure('public.finish_chief_plan(uuid,text,jsonb,text)') as finalizer;
select conname, pg_get_constraintdef(oid) from pg_constraint
where conrelid='public.tasks'::regclass
  and conname in ('tasks_status_check','proposal_is_non_executable');
select count(*) as unexpected_plan_tasks from public.tasks
where plan_run_id is not null and (status<>'proposed' or agent_id is not null);
```

The review table/version must be absent, helpers must match current main, and unexpected
plan tasks must be zero before first application. Review original constraints and the
provider-aware finalizer/claim definitions; stop on drift. Preserve current table counts,
RLS flags and ACLs for comparison. Apply the exact new file atomically through a tracked
migration operation, record only its new version once, and reload PostgREST's schema
cache. This procedure has not been run remotely here.

After application, verify RLS on `task_plan_reviews`, authenticated SELECT-only grants,
anon denial on both review functions, and finalizer EXECUTE denial for anon/authenticated.
Existing rows must be unchanged and old proposals must have null review IDs. Confirm M0
and M1.2 behavior locally and, only with separate authorization, perform hosted acceptance.
There are no new environment variables; do not enable AI planning for this milestone.

## Validation and limits

`npm run check` runs Node/PostgreSQL/domain tests, Python tests, existing mock/planning
HTTP fixtures, the new `test:orchestration-http`, TypeScript and production build. The
HTTP review fixture uses AI disabled and no provider/service-role keys. SQL tests cover
populated M1.2 migration, owner/member/anon and tenant boundaries, exact task/agent
validation, rejected-task retention, idempotency/conflicts, concurrent submissions,
audit rollback, reviewed-task execution denial and M0/provider regressions. Parallel
submissions are exercised through the embedded PostgreSQL runner; separate hosted
PostgreSQL sessions/PostgREST are not tested here. No live AI/API calls occur.

Reviews are final for this milestone. Assignment follows the existing suggested role;
editing, custom role selection, reassignment, partial draft-review saves, re-review and
actual execution are deferred. Unexpected/missing proposal records or agent definitions
block review rather than synthesizing replacements. A future M1.4 must add its own
supervised execution approval and explicitly revise the execution boundary.
