# M1.4 — Supervised Researcher generation

A workspace owner can explicitly authorize one supervised Gemini run for one approved task
assigned to the Researcher definition. The generated requirements/research brief uses
only the mission objective, task title and expected deliverable. It does not browse,
execute tools/code/shell, modify repositories/files, delegate, or verify external facts.
There is no OpenAI fallback, background/scheduled worker or n8n integration.

## Lifecycle and authorization

M1.3 `tasks.status=approved`, assignments and plan review records are preserved. A new
`tasks.execution_status` records `not_authorized → authorized → running → pending_review
→ accepted|rejected`. Failed/interrupted attempts become `failed`; a fresh explicit owner
authorization can retry within a maximum of three attempts per task. Accepted/rejected
results are terminal in this milestone. Plan approval alone never invokes a model.

1. The server action checks a real session, independent execution feature flag and explicit
   confirmation. `authorize_researcher_execution` locks the mission/task and verifies owner
   membership, approved AI mission, accepted task in the original plan-review snapshot,
   current Researcher assignment and completed planning provenance. It creates a separate
   immutable `task_execution_authorizations` record and leased run, then marks the task
   execution `authorized`. Replaying a request ID cannot authorize another call.
2. A separate cookie-free service-role client invokes `start_researcher_execution`, checking
   the run capability, task state, current ownership, assignment and authorization again.
   Only a successful single-use start permits the model request. Developer/Chief of Staff
   tasks and mock/proposed/rejected tasks cannot start.
3. Gemini receives the trusted database inputs, fixed instructions and strict JSON schema.
   The shared Gemini transport is reused; planning retains its 45-second/6,000-token
   settings, while Researcher uses a **30-second deadline, 4,000 output tokens and one
   candidate**. SDK retries and provider fallback are disabled. M1.4.1 optionally permits one additional
   request after HTTP 503, inside the same 30-second total deadline; see below. Sources must be empty and
   verification must equal `not_externally_verified`. Unsupported specifics belong in
   assumptions/questions, never fabricated citations or verification claims.
4. Zod validates the generated document. `finish_researcher_execution_with_diagnostics`
   wraps the original finalizer, which independently checks
   SQL shape/bounds, lease, owner and provenance, then atomically saves a `researcher_document`
   artifact with workspace/mission/task/run IDs, completes the run and changes the task
   execution to `pending_review`. It records the provider's resolved model version when
   returned, retaining the requested model separately. Failure writes no output artifact.
5. Only a current owner can explicitly accept/reject the stored deliverable through
   `review_researcher_deliverable`. Decisions are stored in `task_execution_reviews` with
   actor/time/artifact provenance. Exact duplicate review requests are idempotent; conflicting
   or concurrent decisions cannot overwrite one another. Human acceptance is not external
   verification and does not complete the overall mission automatically.

The existing `runs` and `artifacts` tables are reused. Runs have `purpose=researcher`,
`task_id` and a unique `execution_authorization_id`. The existing mandatory `approval_id`
retains legacy planning provenance only; it **cannot** authorize execution. The new
per-run authorization is required independently by constraints and trusted RPC checks.
Historical runs default to `purpose=mission`; planning display excludes execution runs.
Existing M1.3 plan-status/non-execution constraints remain intact because execution is
tracked separately, not by changing approved tasks to running/completed plan statuses.
Agent worker-enabled flags are not changed by a supervised request.

## Failure, timing and recovery

Authorize/start RPCs have 5-second request deadlines; finalization/recovery/review have
10-second deadlines and explicit `.retry(false)`. Dashboard Server Actions retain the
60-second platform budget. Provider generation is capped at 30 seconds to reserve time
for persistence. Network/authentication/platform delays may still interrupt an invocation;
there is no durable worker continuing after termination. Sanitized `agent_city.researcher`
logs include operation stage, run ID, elapsed time and SQLSTATE/HTTP status when available,
never credentials, capability hashes, prompt/output content or raw provider errors.

A two-minute lease fences starts/finalizers. If a request is interrupted or persistence
cannot be confirmed, refresh first: the transaction may have committed despite a lost
response. An owner can recover only an expired authorized/running attempt. Recovery marks
it failed without a model call; another call needs a new confirmation/request ID. Old
finalizers cannot commit after recovery. Timeouts do not guarantee cancellation or zero
provider billing. Three authorized attempts include claims interrupted before inference. Internal provider
retries do not create another run or authorization.
The existing one-running-run-per-mission index is preserved: active tasks within one
mission are serialized even if several Researcher tasks are approved.

## Environment and UI

Keep `AGENT_CITY_RESEARCHER_EXECUTION_ENABLED=false` by default. After separate activation
approval, execution requires server-only `GEMINI_API_KEY`, optional `GEMINI_MODEL` (existing
`gemini-flash-latest` default), `SUPABASE_SERVICE_ROLE_KEY` and existing user-scoped Supabase
settings. No `NEXT_PUBLIC_` credential variables. The planning flag/provider remain
independent: planning can stay disabled while an existing approved task is executed via
explicit owner authorization. Researcher always uses Gemini, even when planning selects
OpenAI. Existing deliverables can be reviewed and interruptions recovered with execution
subsequently disabled. Confirm Vercel supports the configured 60-second duration.

The task UI distinguishes plan approval from execution state, displays per-run requested
and resolved model (when provided), elapsed time at refresh, safe errors, generated content
and human decisions. It labels all documents as generated and not externally verified;
there are no mock research results, sources or clickable generated external links. No
continuous polling/background process is added. Model output can be inaccurate; human
review is required and this milestone performs no external evidence verification.

## Gemini failure diagnostics

Server logs under `agent_city.researcher` (and `agent_city.planning`) now include
`stage=generation`, `outcome=failed`, `httpStatus` and `failureClass` for non-2xx
Gemini responses: 400 invalid_request_or_schema, 401 authentication, 403 permission_denied,
404 model_or_endpoint_unavailable, 429 quota_or_rate_limit, 5xx server_error.
These are status-based categories, not a diagnosis of a specific API key, model or quota.
Error bodies are never read, retained or logged. Database failure codes and attempt
limits remain unchanged; fallback is unavailable. The optional M1.4.1 retry is described below. Network errors/timeouts have
no HTTP status. Existing failed attempts are not reset.

Researcher and planning use the same endpoint, headers and JSON request envelope.
Researcher retains its 30-second/4000-token limit (planning: 45 seconds/6000 tokens).
The Researcher `verification` literal previously emitted JSON Schema `const`;
Gemini's [official documented subset](https://github.com/googleapis/js-genai/blob/main/src/types.ts)
(`GenerateContentConfig.responseJsonSchema`) lists `enum`, not `const`.
The Gemini transport now converts that keyword to a single-value `enum`; local Zod/SQL
validation, empty sources (`maxItems=0`), and all other constraints remain unchanged.
Planning's schema is unchanged. This fixes a documented compatibility mismatch but does
not establish why the historical runs failed: their HTTP status was discarded.
To diagnose another explicitly authorized attempt, inspect the sanitized generation
log for its run ID. Do not infer provider success from a running/failed run or bypass
remaining attempt limits. No live provider/model availability check is part of this fix.

## M1.4.1 reliability and acceptance checklist

Evidence: Researcher run `03e26f03-f0f7-4747-bf66-e059e1ead043` received HTTP 503
about 500 ms after a valid claim/start, then finalized failure successfully. This proves
an upstream server-error response and functioning failure persistence, not its underlying
cause or that a different model would succeed. No speculative schema/model change is made.

`AGENT_CITY_RESEARCHER_503_RETRY_ENABLED=false` is the default. With explicit `true`, only
the first HTTP 503 may receive one additional request in the same owner-authorized run.
The sole exponential backoff interval is 250 ms plus 0–250 ms jitter. Each request retains
4000 output tokens/one candidate. Both requests and backoff share a total 30-second budget;
the second gets only the remaining time and is skipped unless at least one second remains
after backoff. No automatic retry for any other status, timeout/ambiguous response,
invalid JSON/schema, network failure or persistence error; never provider/model fallback.
A quick 503 plus successful retry can cost up to two requests. A failed/aborted request
may still be billed; this is a request-count bound, not a monetary guarantee. The owner
consent label now explicitly covers up to two potentially paid requests per authorized run.
Three authorized runs per task remain the database limit; existing counters are untouched.

Generation is also capped at 45 seconds from action entry, reserving ten seconds for
finalization plus five seconds margin against the page's 60-second budget. RPCs share a
55-second action signal and retain 5-second claim/start and 10-second finalization bounds.
A conservative lease bound is 110 seconds from claim initiation (the database lease starts
later and lasts 120 seconds); PostgreSQL revalidates the lease on finalization. Authentication
or platform termination can still interrupt the action; no background work is started.
Actual hosted runtime support must be verified before enabling execution or retry.

Per-request sanitized logs include run ID, request number, requested/resolved model when
available, HTTP status/class, retry eligibility and scheduled/performed/skipped decision,
provider elapsed time and application deadline versus transport failure. Existing outer
stage logs record atomic persistence outcome. Failed runs now retain public bounded
`execution_metadata`: request count, retry performed, last HTTP status/class, elapsed time,
last timeout source. These fields are stored in the same transaction as run completion and
artifact persistence. Historical/interrupted rows may have null metadata; the UI explicitly
says details are unavailable instead of implying zero provider requests. A failure of the
metadata finalizer remains an ambiguous persistence outcome, never another model call.

Hosted checklist (manual; not performed by this implementation):

1. Keep execution and retry flags false. Verify the deployed branch, existing M0–M1.4
   schema, `runs.purpose`, `resolved_model`, original five-argument finalizer, owner/start/
   finish privileges and 120-second lease. Inspect remote history without reconciling IDs:
   historical remote M0/M1.1 IDs differ and M1.2 was applied manually. Stop on drift.
2. Apply **only** `supabase/migrations/20261022150000_researcher_reliability.sql` through an
   atomic tracked migration after review. Never db push or replay historical migrations.
   Apply it before deploying M1.4.1: the dashboard reads the new column even with execution
   disabled. It adds nullable `runs.execution_metadata`, a strict pure validator/constraint and a new
   six-argument service-role-only wrapper; the old five-argument RPC remains compatible.
   Verify existing rows/artifacts/counters are unchanged, RLS and SELECT-only client table
   grants remain, and anon/authenticated lack EXECUTE on both new finalizer functions.
3. Confirm server-only Supabase URL/publishable/service-role keys and Gemini API key.
   `AGENT_CITY_MODE=supabase`; execution remains opt-in. No NEXT_PUBLIC secrets.
   Planning settings stay independent and need not be enabled for an approved task.
4. Model recommendation for separate review: Google's official
   [model listing cookbook](https://github.com/google-gemini/cookbook/blob/main/quickstarts/Models.ipynb)
   and [structured JSON example](https://github.com/google-gemini/cookbook/blob/archive/generate-content-api/quickstarts/JSON_mode.ipynb)
   list/use `gemini-3.5-flash`, an explicit non-preview versioned model rather than the
   moving `gemini-flash-latest` alias. Documentation is not proof of availability, quota,
   free-tier access or pricing for this project. Check official current model metadata,
   structured-output support, project access and quota before approving `GEMINI_MODEL`.
   No default/model was changed here; the variable affects BOTH planning and Researcher.
5. Verify Vercel's effective runtime is at least 60 seconds and honors dashboard maxDuration;
   inspect region/network and expected claim/finalization latency. Do not enable retry if
   that budget cannot be guaranteed. No higher runtime/provider deadline is requested.
6. Enable execution explicitly; leave retry false for the first baseline acceptance test.
   If approved after budget/cost review, enable the retry flag for a separate authorized
   test. Use one small approved Researcher task with an available attempt and fresh owner
   consent. Do not use a historical exhausted task or reset counters. Do not force a live
   503 to test retry: the deterministic offline fixture covers that path.
7. Correlate `claim/start`, numbered `generation` and `finalize_plan|finalize_failure` events
   by run ID. Success: one run/authorization, one generated artifact, task pending_review,
   requested/resolved model and bounded metadata; failure: failed task/run, no artifact,
   safe reason/status and a new authorization required before another execution.
8. Inspect the structured preview and explicitly accept or reject it as owner. Confirm
   the review/audit entry; no task execution, external verification or autonomous work follows.
9. Rollback: disable retry immediately; disable execution too if needed. Allow in-flight
   bounded work to finish; refresh before recovering only expired runs. Revert application
   deployment if required, retaining the additive schema, historical metadata and artifacts.
   The old finalizer remains available for the older application. Do not drop columns,
   replay migrations, delete runs or reset counters. Existing results remain reviewable.

Offline verification includes immediate success, 503 success/exhaustion, prohibited retries,
